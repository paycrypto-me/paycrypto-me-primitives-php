# PIP-0003 — Public Address Derivation

Origin: [paycrypto-me/paycrypto-me-primitives-php#3](https://github.com/paycrypto-me/paycrypto-me-primitives-php/issues/3) (retrospective coordination anchor; the historical PIP predates the Issue-origin rule).

This is the consolidated reference for the first Primitives capability as of
2026-10-07.
PIP-0001 documented the earlier plan rewrite and PIP-0002 documented provider
research; their issued records retain their own identities and exact Git history.
This consolidation does not turn those records into a single historical proposal
or assert approval under the current PIP Specification.

## Motivation

The accepted Primitives architecture is grounded in one concrete requirement:
derive a Bitcoin receiving address from an extended public key without handling
private material. The early work split documentation repair, provider research,
and capability delivery across three PIPs before the PIP process was stable.
Keeping three active entry points obscures the present scope and the distinction
between research, contract drafts, accepted architecture, and verified behavior.

## Materiality

This consolidation changes documentation and navigation, not an accepted
architectural decision. The [Primitives canonical v1.8](../../canonicals/primitives/paycrypto-primitives-canonical-architecture-reference-v1.8.md)
already admits public derivation and the three initial Bitcoin address
constructions. Under the [PIP Specification v1.0](../../specifications/paycrypto-pip-specification-v1.0.md),
the Materiality Gate therefore does not justify creating PIP00004, renumbering
this historical record, or treating its existence as approval for execution.
Issue #3 remains the work and navigation anchor. A later change to an accepted
decision must return to the Materiality Gate on its own Issue.

PIP-0003 was created before Issues were required to originate PIPs. Issue #3 was
created afterward, and it has no recorded `PIP Decision = Approved` with an exact
approved proposal SHA. This historical exception cannot be repaired
retroactively. No new Execution Plan is created by this consolidation; the old
milestone package is recoverable as historical work, not approval evidence.

## Proposed change

Deliver a locally usable, public-key-only Primitives operation with explicit
extended public key, relative non-hardened public path, validated Bitcoin network
definition, and address policy as inputs. It yields an address or a defined
failure. The complete initial capability covers P2PKH, P2SH-P2WPKH, and P2WPKH
on mainnet and testnet. The three constructions share derivation and other
compatible lower capabilities, diverging where their address semantics differ.

Primitives owns admission, semantic contracts, invariants, protocol operations,
definitions, failures, and composition. Cryptographic algorithms, curve
mathematics, and standardized codecs are delegated to qualified libraries or
runtime facilities. Provider APIs and types stay behind semantic boundaries.
At this consolidation checkpoint, no production provider or PHP API had been
selected.

## Scope

The capability includes strict extended-public-key admission, bounded public
derivation, validated network and policy compatibility, the three address
constructions, explicit provider wiring, and a standalone usage example. Network
variation is validated data. BIP32 derivation semantics and SLIP-132 version or
policy interpretation remain distinct; no reference application's fixed path,
account depth, or implicit policy becomes a domain rule.

The first delivery remains limited to public material. It excludes seeds,
mnemonics, private or hardened derivation, signing, transactions, address
allocation or persistence, usage discovery, payment state, hosted integration,
fixed-address validation, Taproot, Bech32m, Lightning, and additional chains.
Bitcoin Cash is a bounded reuse check, not a delivered capability. Core, SDK,
Consumer, and external-project implementations are outside this repository's
delivery scope.

Evidence for the delivered capability must establish correct public derivation,
all six policy/network combinations, negative and rare outcomes, local use,
provider containment and replaceability, and independent expected results on the
supported PHP 8.1 and 8.3 runtimes. Technical Counter-Proof obligations are set
by the current Primitives canonical and reporting protocol, independently of
whether this historical PIP has an approval field.

## Open questions

The [M01 contract draft](milestones/M01-CONTRACTS.md) is the most detailed current
statement of requirements R01–R12, qualification criteria Q01–Q12, and unresolved
decisions O01–O07. It is a draft, not a frozen PHP API or verified implementation.
The unresolved questions are:

1. Exact-index versus advancing public derivation, effective-path reporting,
   invalid-child outcomes, exhaustion, and bounded work.
2. Supported public versions and explicit key, network, and policy compatibility.
3. Serialized versus prevalidated input, result fields, and validation ownership.
4. Relative-path grammar, empty path, depth, index and host-integer limits.
5. Definition representation, validation, and unknown-field handling.
6. Stable failure meanings, adapter obligations, and safe diagnostics.
7. Qualified providers, codec alternatives, runtime/extension support, actual
   dependency paths, and independent reference evidence.

The [provider worksheet](../../research/public-address-provider-research.md)
contains preliminary candidates and bounded probes. These do not qualify an
adapter or select a production dependency. Selection remains an explicit later
decision supported by versioned evidence. At the research checkpoint,
`bitwasp/bitcoin` was excluded from production options for this slice on
footprint grounds and retained as reference evidence; its separate focused
Bech32 package remained a candidate. Those are historical candidate
dispositions, not architectural rules or a completed production selection.
